### **ADR-0164: Separación de Repositorios para Código y Contexto de Agentes**

**¿Qué decidimos?**

Drasus se divide en dos repositorios con una dependencia en una sola dirección:

- `Drasus-Engine` conserva el producto: código Rust y Flutter, migraciones, datos de prueba, documentación de dominio y adaptadores propios del producto.
- `Drasus-Context` se convierte en la fuente canónica del sistema de agentes: skills, knowledge, plantillas, hooks, catálogo, runtime `drasus_context`, pruebas y artefactos de plataforma generados.
- `Drasus-Engine` consume una revisión fijada de `Drasus-Context` mediante un submódulo Git en `.agents` durante la primera migración. La revisión fijada funciona como contrato reproducible del contexto que usa el motor.
- `AGENTS.md`, `CLAUDE.md` y las proyecciones específicas de plataforma que deban vivir en la raíz del proyecto quedan como adaptadores del producto. Su contenido compartido se genera desde `Drasus-Context`; no se mantienen copias manuales de las reglas.

**¿Por qué lo decidimos?**

El historial y el ciclo de cambio del producto no coinciden con los del sistema de agentes. Mantenerlos en el mismo historial mezcla revisiones, dificulta aislar regresiones y hace que una modificación de gobernanza parezca un cambio del producto. La separación permite revisar, versionar y probar cada sistema con su propio dueño sin perder reproducibilidad en el motor.

**¿Qué restricciones tiene? (FIJO)**

- Ningún cambio nuevo en skills, knowledge, hooks, catálogo o runtime se implementa directamente en `Drasus-Engine`.
- Ningún cambio de código, migración, UI o decisión de dominio se implementa en `Drasus-Context`.
- `Drasus-Engine` solo actualiza la revisión fijada de `Drasus-Context` después de validar la compatibilidad del conjunto.
- Los adaptadores generados no son fuentes de verdad y no se editan manualmente.
- La extracción inicial puede preservar el historial relevante en `Drasus-Context`, pero no reescribe el historial público de `Drasus-Engine`.
- Los planes y registros operativos de agentes pertenecen a `Drasus-Context`; las decisiones de producto y las órdenes de implementación pertenecen a `Drasus-Engine`.
- El runtime `agentic-mcp-gateway` del producto queda fuera de `Drasus-Context`.

**¿Cómo se vería en el sistema?**

- Un checkout de `Drasus-Engine` obtiene una revisión concreta de `Drasus-Context` y puede validar el catálogo y el runtime sin depender de archivos residuales de otra máquina.
- Una modificación de una skill produce una revisión en `Drasus-Context`; `Drasus-Engine` solo registra el cambio de revisión y ejecuta su comprobación de compatibilidad.
- Una modificación de una feature de producto no modifica el historial de `Drasus-Context`.
- La matriz de propiedad de [`REPOSITORY-OWNERSHIP.md`](../REPOSITORY-OWNERSHIP.md) resuelve la ubicación de cada familia de archivos durante la transición y después de ella.

**¿Qué cuesta?**

La separación añade coordinación entre dos repositorios, una operación de actualización del submódulo y pruebas de compatibilidad. También exige distinguir las fuentes canónicas de los adaptadores de plataforma. Ese costo es menor que seguir mezclando cambios de gobernanza, runtime y producto en un mismo historial.
