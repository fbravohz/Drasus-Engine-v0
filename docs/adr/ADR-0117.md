> 🔶 **Enmendado por ADR-0165 y ADR-0166** — se conserva la entrega progresiva de Cáscaras y SVF; la implementación usa Tauri + React y gRPC. Cada mutación observable de un agente se representa desde su operación durable, no por automatización de interfaz.
>
> 🔶 **Enmendado por ADR-0152** — el "Banco de Verificación" se formaliza como la feature [`verification-bench`](../features/verification-bench.md): un harness genérico que se convierte en criterio permanente de Definición de Terminado. Toda Feature, incluida plomería, necesita una vista propia con su resultado u observable real en el Banco para cerrar Etapa 5 (QA).
>
> 🔶 **Enmienda de entrega visual vigente** — toda Orden de implementación de Feature entrega las tres superficies: vista/observable real en el Banco, nodo Canvas conectable con inspector lateral desplegable a vista completa y widget Dashboard. Aplica también a plomería; su vista puede ser de solo lectura y su widget queda desactivado en producción. La ausencia de infraestructura se resuelve dentro de la Orden o deja el cierre parcial. La condición previa que permitía diferir el nodo Canvas queda supersedida.

### **ADR-0117: Entrega Progresiva de Cáscara Delgada por Feature — Techo Fijo, Ventana de Verificación y Redefinición de EPIC-8 como Unificación ZUI**

*   **Decisión:**
    Se sustituye la regla "máximo una pantalla utilitaria por fase (EPIC-1–EPIC-7), pulido reservado a EPIC-8" por: **cada Orden de implementación de Feature entrega sus tres representaciones compartidas junto con el backend**, bajo un **Techo Fijo**. Las Features con superficie propia incluyen la operación y su resultado; plomería puede exponer solo su observable real, sin interacción. Toda Feature de plomería declara además una **Ventana de Verificación** —su consumidora y el observable integrado—, que complementa pero no sustituye sus tres entregables. SPIKE-006 (EPIC-0) dejó el **Panel Operativo Fundacional** como shell Tauri/React real y persistente, con vistas transversales iniciales de [`clock`](../features/clock.md), [`async-job-executor`](../features/async-job-executor.md) y [`audit-log`](../features/audit-log.md).

*   **Objetivo:**
    El diseño de Drasus ya es full-stack por Feature (cada spec describe conceptualmente su contrato de UI); diferir toda la interfaz a EPIC-8 generaba tres costos: (1) evidencia de "round trip" front→back→DB→front tardía, justo cuando CONTENT-STRATEGY.md (Pilar G "Building in Public") más la necesita desde EPIC-0; (2) un inventario "qué falta de UI" al llegar a EPIC-8, propenso a huecos y retrabajo; (3) pérdida de la señal de verificación visual diaria que el desarrollador (con trayectoria frontend) usa para confirmar que el sistema funciona. El "techo fijo" existe para que esta entrega progresiva no infle cada Story 2-3x: el alcance de UI es exactamente lo necesario para DEMOSTRAR que la Feature funciona, no una reconstrucción de producto.

*   **Reglas:**
    - **Techo Fijo — evidencia visual (FIJO):** toda Feature muestra el resultado real de su operación por `public_interface` y gRPC, junto con un observable que siga visible tras recargar. En plomería, una vista transversal read-only del estado, conteo, timestamp o resultado satisface este propósito sin exigir interacción. No se crean rutas de transporte solo para UI ni se usan datos mock como evidencia.
    - **Límites del Techo (FIJO):** un único shell compartido alberga el **Banco de Verificación**, con registro central y construcción bajo demanda. Cada Feature tiene una vista propia dentro del Banco, aunque use solo estado de lectura. La Feature conserva su contrato de **Ventana de Verificación** para identificar consumidor y observable integrado; esa ventana no sustituye la vista propia.
    - **Tres representaciones por Orden de Feature (FIJO):** (1) vista/observable real en el Banco; (2) nodo Canvas conectable con inspector lateral y control para desplegar el mismo detalle a vista completa; (3) widget read-only en Dashboard. Los widgets de producto quedan habilitados; los de plomería se desactivan en producción. El inspector conserva selección y estado de edición entre modos. QA verifica las tres representaciones con datos reales.
    - **Gate de Integración Anti-Deuda (FIJO):** una Orden de Feature no cierra `Completado` hasta verificar las tres representaciones obligatorias y, para plomería, el observable de su Ventana de Verificación. Si falta infraestructura, la Orden incluye el alcance habilitante o permanece parcial; no se difiere el entregable a EPIC-8 como deuda.
    - **Redefinición de EPIC-8 → Canvas [Forge/Reactor — TBD] y Pulido (FIJO):** EPIC-8 unifica y pule las superficies progresivas, construye infraestructura compartida del Canvas cuando no se haya entregado antes, añade widgets avanzados, visualizadores que requieren datos agregados de varias fases (UMAP, parallel-coordinates, tiempo de corrida, etc.) o diferidos por SPIKE-005/ADR-0115, y empaqueta el producto (ADR-0029). La ausencia de infraestructura Canvas no permite cerrar una Orden de Feature sin nodo.
    - **SPIKE-006 → Panel Operativo Fundacional (FIJO):** la salida de SPIKE-006 (host Tauri, React, gRPC y stream recuperable con downsampling/throttling) es la primera Cáscara Delgada real, no un experimento descartable: muestra vistas transversales reales del reloj determinista, la cola del ejecutor de trabajos y la bitácora de auditoría. Cada Orden de esas Features entrega además sus tres representaciones propias según este ADR.

*   **Implementación:**
    Cada Orden que implemente una Feature entrega, junto al backend Rust y contratos gRPC, sus tres representaciones: vista/observable en el Banco, widget en Dashboard y nodo Canvas conectable con inspector lateral/desplegable. Las tres usan datos reales; la plomería puede ser read-only y su widget queda desactivado en producción. Si falta infraestructura, se implementa dentro de la Orden o el cierre permanece parcial. El Banco usa registro centralizado y construcción bajo demanda; desde EPIC-0 existe una aplicación Tauri/React real y creciente, no prototipos desechables.

*   **Costo:**
    Cada Orden de Feature incluye el trabajo mínimo para sus tres representaciones, acotado por el Techo Fijo. QA verifica el gate de integración antes del cierre. EPIC-8 conserva la unificación ZUI, el pulido, los visualizadores avanzados y el empaquetado comercial.
