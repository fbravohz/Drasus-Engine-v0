> 🔶 **Enmendado por ADR-0165 y ADR-0142:** se conserva el Banco como gate funcional por feature. La UI Flutter y el transporte FFI de la entrega anterior quedaron retirados; la nueva UI será Tauri/React y llamará al Core local por gRPC, después del Spike requerido por ADR-0142.

### **ADR-0152: Banco de Pruebas como Gate Permanente de Definición de Terminado — Realización Canónica de la Superficie de Verificación Funcional Genérica**

*   **Decisión:**
    Ninguna feature con superficie propia se considera terminada en Etapa 5/QA sin una verificación individual en el Banco de Pruebas, conforme a ADR-0117. El Banco es un harness funcional compartido que ejecuta la operación real de una feature por su contrato público y muestra el resultado; permite verificar features por separado sin componer todo el producto.

*   **Contexto y estado:**
    ADR-0117 exige una Superficie de Verificación Funcional por feature. [STORY-050](../execution/STORY-050-verification-bench.md) entregó la primera versión Flutter/FFI y conectó 15 features; por eso `DEBT-005` sigue pagada para ese trabajo. ADR-0165 retiró Flutter como cliente activo. La aplicación Tauri/React actual aún no contiene el Banco; la versión nueva queda pendiente y no reutilizará el catálogo de widgets Flutter.

*   **Modelo funcional del Banco:**
    - **Selector de feature:** presenta cada feature conectada mediante una entrada del registro del Banco.
    - **Panel de verificación:** ofrece entrada editable y respuesta de solo lectura. Puede conservar el formato de tres zonas de la especificación anterior; sus detalles visuales se actualizan con ADR-0135 antes de implementar.
    - **Validación de forma:** identifica input mal formado antes de invocar la operación real y explica la causa. Distingue este caso de un fallo de la operación.
    - **Ejecución aislada:** verifica una feature por envío, mediante su interfaz pública y su contrato gRPC. No requiere conectar entre sí todas las features del producto.

*   **Reglas:**
    - **Gate de Definición de Terminado (FIJO):** una feature con superficie propia requiere su conexión individual al Banco para cerrar Etapa 5/QA. Si el Banco no está disponible en el cliente vigente, registra el observable pendiente y su integración según AGENTS.md y ADR-0117; no presentes la feature como verificada por el Banco.
    - **Un solo punto de extensión (FIJO):** integrar una feature consiste en registrar su operación de verificación y su entrada de ejemplo; el harness compartido conserva selección, validación y presentación del resultado.
    - **Una sola lógica de dominio (FIJO):** el Banco invoca la interfaz pública Rust de la feature por el adaptador gRPC; no replica ni deriva lógica de negocio en React.
    - **Datos reales, nunca mock (FIJO):** el resultado visible proviene del Core local. El Banco no depende de la Cabina de Mando ni de servicios centrales para verificar el comportamiento local.
    - **Contrato de transporte (FIJO):** la UI Tauri/React consume el contrato Protobuf y los bindings establecidos por ADR-0165. No se añaden DTOs manuales ni rutas de transporte especiales para el Banco. La validación de input se define con el Spike requerido por ADR-0142, sin reabrir la fuente Protobuf.
    - **Independencia de canales (FIJO):** el CLI `drasus verify` y el Banco son canales independientes que llegan a la misma lógica pública de la feature; un fallo de uno no sustituye ni oculta al otro.
    - **Sin nodo Canvas (FIJO):** el Banco es plomería transversal; no produce un tipo de dominio ni un nodo propio del Canvas, conforme a ADR-0137.

*   **Implementación pendiente:**
    La especificación vigente de [`verification-bench`](../features/verification-bench.md) conserva decisiones funcionales de la versión anterior, pero sus referencias a Flutter, FFI, `custom_ui` y galería de widgets son históricas. La nueva implementación requiere primero el Spike de gRPC de ADR-0142 y después una Story Tauri/React que adapte la ficha y conecte las features según este gate. El pago histórico de `DEBT-005` no acredita que el Banco esté disponible en el cliente actual.

*   **Costo:**
    El harness se construye una vez. Cada feature añade una entrada de registro, un input de ejemplo y su verificación real; el contrato público conserva la lógica en Rust.

*   **Trazabilidad:** ADR-0117 (Cáscaras y Ventanas de Verificación), ADR-0135 (Cáscara Visual), ADR-0136 (contextos Dashboard/Canvas), ADR-0137 (puertos tipados), ADR-0142 (CLI y Spike gRPC), ADR-0143 (plano central), ADR-0165 (Tauri/React y gRPC), [`verification-bench`](../features/verification-bench.md), [STORY-050](../execution/STORY-050-verification-bench.md), `DEBT-005`.
